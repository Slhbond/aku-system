# Q7：基线是测试原设备的原固件吗？

## 你的问题

> 基线是测试原设备的原固件吗

## 直接回答

**理论上是的，但你这里有个硬约束：**

> 小白的原固件在 AKU 上**根本起不来**（NAND 品牌不同，一直重启）—— 正是这个原因才有了整个项目。

所以「在 AKU 上跑原厂固件测基线」这条路**是堵死的**。

## 三层基线方案

| 层级 | 怎么测 | 前提 | 可行性 |
|---|---|---|---|
| **A. 真·原厂基线** | **小白设备 + 小白原厂固件** | 小白还在你手上 | ✅ 最理想 |
| **B. 绝对基线** | 用**芯片理论上限**当标尺 | 无 | ✅ **随时可做，推荐** |
| **C. 相对基线** | AKU+Ubuntu vs AKU+Alpine | 你现在就有 | ✅ 现在就能做 |

### 关于 A

小白和 AKU **只差 NAND 品牌，射频部分完全相同**（同一套 PCB、同一个 AP6212 模组、同一条天线）。
**NAND 不影响 WiFi/蓝牙**，所以小白的数据**完全可以当 AKU 的参照**。
唯一差别是「两台不同机器」的个体差异，很小。

### B 才是最实用的

BCM43438 是 **802.11n 1×1 20MHz**：
- 理论 PHY 速率 **72.2 Mbps（MCS7）**
- 实测 TCP 吞吐天花板约 **35 Mbps**

```bash
iw dev wlan0 link
# 近距离能协商到 72.2 Mbit/s → PHY 已拉满，射频层面没得可捞了
# 只有 39 / 26 / 13 Mbit/s  → 还有优化空间
```

**这比「跟原厂比」更有意义，因为原厂也不可能超过芯片上限。**

## 原厂系统怎么测（工具情况）

原厂系统里**没有 `iw`、没有 `iperf3`**，但有：

| 工具 | 有吗 | 用途 |
|---|---|---|
| `wget`（busybox + /usr/bin） | ✅ | 测吞吐 |
| `nc` | ✅ | TCP 打流 |
| `telnetd` / `adbd` | ✅ | 进去拿 shell |
| `iw` / `iwconfig` / `wpa_cli` | ❌ | 看不了协商速率 |
| `cat /proc/net/wireless` | ✅ | **能看信号质量（不需要 iw）** |

```sh
# 原厂上（telnet 或 adb 进去）
cat /proc/net/wireless                            # link quality / level / noise
wget -O /dev/null http://<PC_IP>:8000/test.bin    # 吞吐
```

PC 上先起个服务：
```bash
python -m http.server 8000    # 目录里放个 100MB 的 test.bin
```

**Ubuntu / Alpine 上要补工具**（我查了，两个系统默认都没有）：
```bash
apt install iperf3 iw     # Ubuntu
apk add iperf3 iw         # Alpine
```

## 最小可执行方案

| 测量项 | 命令 | 小白+原厂 | AKU+Ubuntu | AKU+Alpine |
|---|---|---|---|---|
| 信号质量 | `cat /proc/net/wireless` | | | |
| 协商速率 | `iw dev wlan0 link` | 做不了 | | |
| TCP 吞吐 | `wget` / `iperf3` | | | |
| 蓝牙掉音距离 | 走到哪开始卡 | | | |

**三条纪律：**
1. **同一时间、同一位置、同一 AP** —— 2.4GHz 很挤，不同时段的数据没法比
2. **每个点测 3 次取中位** —— 单次读数波动很大
3. **蓝牙也量距离** —— 蓝牙音箱的「效果」主要就是这个，比吞吐重要

## 结论

如果只有 AKU 一台机器，用 **B（芯片上限）+ C（两套互比）** 就够判断了：
- **B 告诉你「到顶了没有」**
- **C 告诉你「哪套配置更好」**
- 结合就能推断「还差多少」，不一定非要原厂的数字
