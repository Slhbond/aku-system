# Q5：原固件是小白，设备是 AKU，只差存储品牌

## 你的补充

> 我给你看的原固件是小白的大佬适配的设备是 aku
> 这两个设备就储存品牌不一样导致小白刷了之后一直重启

## 这条信息解释了整个项目的起因

| | **小白** | **AKU**（目标设备） |
|---|---|---|
| 设备 | 我最初分析的 `aku原固件.zip` 其实来自**小白** | 大佬适配的目标 |
| 硬件差异 | **只有 NAND Flash 品牌不同** | |
| 结果 | 小白固件刷上去 → **一直重启** | 所以必须重做系统 |

## 为什么换个 NAND 品牌就会一直重启

### 机制

全志 BROM 上电后从 NAND 读 Boot0(SPL)，用的是它**按 NAND ID 自己决定的页大小 / OOB / ECC 方案**。

而刷机脚本里这一步是关键：

```
nand write.raw.noverify 0x83000000 0 40      ← 把 sunxi-spl-with-ecc.bin 原样写入 NAND
```

- `sunxi-spl-with-ecc.bin` 的 **ECC 是预先算好的，按特定 NAND 几何生成**（文件名里的 with-ecc 就是这个意思）
- `.raw` + `.noverify` = **原样写入、不重算 ECC、不校验**
- 末尾的 `40` 是**按页数**算的

**→ 换成页大小 / OOB / ECC 不同的 NAND，这个预生成镜像就对不上，**
**→ BROM 读不出 SPL → 反复重试 → 现象就是「一直重启」。**

### 为什么 mainline 能解决

主线 **U-Boot 2023.01 + `sunxi_nand`** 用 **ONFI / NAND ID 自动探测**几何参数，
不再依赖厂商那套写死的表 —— 换 NAND 品牌也能自适应。
**这正是必须做 mainline 移植的根本原因。**

## ⚠️ 对以后刷机的直接影响

| 场景 | 要做什么 |
|---|---|
| 支持第三种 NAND | `sunxi-spl-with-ecc.bin` 必须用 `sunxi-nand-image-builder`（sunxi-tools）**按新 NAND 的几何重新生成** |
| 同上 | `nand write.raw` 的**页数参数也要一起重算** |
| 任何刷机前 | 先做**整片 NAND 备份**（分区级备份不含 Boot0/U-Boot，救不了砖） |

## 另一个重要含义

**小白和 AKU 的射频部分（PCB、AP6212 模组、天线）是同一套设计**，只差 NAND。
→ 所以**小白的 WiFi/蓝牙性能数据可以当 AKU 的参照**（见 [`Q7_基线怎么定义.md`]）。
