# Q3：文件夹里的 08 是什么？

## 你的问题

> 文件夹里的08是啥意思

## 回答

那不是文件夹，是一张**故障单**：

```
文件名：08_UDISK元数据损坏说明.txt
（原为 08_udisk_元数据损坏说明.txt）
内容：
  UDISK 完整镜像 (nandi-data3.img, 3.6 GB) 的 ext4 元数据损坏:
    - 带 needs_recovery 标志且 journal 损坏
    - 7-Zip / debugfs 均无法遍历目录树
    - e2fsck -fy 修复后只恢复出 11 个 inode
```

### 编号规则

`00`~`10` 只是我加的**排序前缀**，让目录按分析流程排整齐：

| 编号 | 内容 |
|---|---|
| 00_raw | 原始分区镜像 |
| 01_uboot | U-Boot（环境变量） |
| 02_kernel_dts | 内核 + DTS |
| 03_logos | 图标 / 开机图 |
| 04_rootfs | 根文件系统解包 |
| 05_report | 分析报告 |
| 06_ipk | 应用安装包 |
| 07_overlay | 可写层（应用实际装在这） |
| **08** | **本来是 `08_udisk_full/`（UDISK 全盘解包），失败了** |
| 09_app_resources | 应用资源（表情 / 语音） |
| 10_移植系统资料 | 移植系统资料 |

### 为什么失败

备份里有两个 UDISK 相关文件：
- `UDISK_backup.bin`（238 MB）—— **被截断的残片**
- `nandi‑data3.img`（3.6 GB）—— **完整的 UDISK 分区**，同一个 ext4

尝试过程：
1. 7-Zip → `Cannot open the file as archive`
2. `debugfs` → `Illegal block number … / Ext2 inode is not a directory`
3. 裁到 ext4 精确长度重试 → 仍失败
4. WSL 上 `e2fsck -fy` 修复 → **只捞回 11 个 inode**（只剩 `lost+found`）

### 但这事没影响

奇怪的是**文件数据物理上还在** —— 扫原始镜像命中了 `.gowild_config` 195 次、`gowild` 2168 次。
坏掉的只是**目录索引**。而且这批内容在 `xxb-robot-swapp` 的 ipk 里有完好的一整份。

## 结论
**该拿的一分没少**（419 个文件在 `04_原固件解包/09_app_resources/`）。
