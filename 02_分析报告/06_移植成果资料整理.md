## 1. 一句话结论

**大佬做的是一次彻底的 mainline 移植，不是我之前猜的"保留原厂内核换用户态"。**
原厂那套 Linux 3.4.39 + fex 已经被完全抛弃，现在是 **Linux 6.1.9 主线 + 设备树 + U-Boot 2023.01 + UBIFS**。

三块"硬骨头"的答案是：

| 难题 | 原厂做法 | 大佬的解法 |
|---|---|---|
| **显示屏** | 全志 DISP/TCON + fex `[disp_init]` + DirectFB | **自写 ST7735S framebuffer 驱动**，编进内核 |
| **音频** | ASoC **FPGA** 驱动（`zhc_function.ko`） | **绕过 FPGA**，走主线 `sun4i-a10-codec` + PA GPIO + `asound.state` |
| **WiFi/蓝牙** | 闭源 `bcmdhd.ko` + Broadcom **BSA** 协议栈 | 主线 `brcmfmac` + **原厂 NVRAM 原样复用** + 一整套 BlueZ 5.85 / bluez-alsa |

### 1.1 ⭐ 背景：为什么要做这次移植 —— 存储品牌不同

| | **小白** | **AKU** |
|---|---|---|
| 设备 | 我最初分析的 `aku原固件.zip` 其实来自**小白** | 大佬适配的目标设备 |
| 硬件差异 | **只有存储（NAND Flash）品牌不同** | |
| 结果 | 小白固件刷到 AKU 上 → **一直重启** | 所以必须重做 |

#### 为什么换个 NAND 品牌就会一直重启

全志 BROM 上电后从 NAND 读 Boot0(SPL)，用的是它**按 NAND ID 自己决定的页大小 / OOB / ECC 方案**。
而刷机脚本里这一步是关键：

```
nand write.raw.noverify 0x83000000 0 40      ← 把 sunxi-spl-with-ecc.bin 原样写入 NAND
```

- `sunxi-spl-with-ecc.bin` 里的 **ECC 是预先算好的，按特定 NAND 几何生成**
- `.raw` + `.noverify` = **原样写入、不重算 ECC、不校验**
- 末尾的 `40` 是**按页数**算的

→ 换成页大小 / OOB / ECC 不同的 NAND，这个预生成镜像就对不上，
**BROM 读不出 SPL → 反复重试 → 现象就是“一直重启”**。

#### 这也是必须做 mainline 移植的根本原因

主线 **U-Boot 2023.01 + `sunxi_nand`** 用 **ONFI / NAND ID 自动探测**几何参数，
不再依赖厂商那套写死的表 —— 换 NAND 品牌也能自适应。

> **对以后刷机的直接影响**：如果要支持第三种 NAND，
> `sunxi-spl-with-ecc.bin` 必须用 `sunxi-nand-image-builder`（sunxi-tools）
> **按新 NAND 的几何重新生成**，`nand write.raw` 的页数参数也要一起重算。

### 2.2 NAND 几何（来自 `mkrootfs.sh`，关键参数）

```
mkfs.ubifs -r ./ubuntu-rootfs -o ubifs.img \\
  -m 8192        # 最小 I/O = 8 KiB（页大小）
  -e 2080768     # LEB = 2 MiB - 2*8 KiB
  -c 2048        # 最大 LEB 数
  -x lzo         # LZO 压缩
  -F             # 允许空白空间

ubinize -o rootfs.ubi -m 8192 -p 2097152 -s 8192 ubinize.cfg
                 #            ^PEB=2MiB  ^子页=8KiB
```

→ **页 8 KiB / 擦除块 2 MiB / 子页 8 KiB**，UBI 卷：`vol_id=0, vol_name=rootfs, vol_type=dynamic, vol_flags=autoresize`

## 3. 三个"硬骨头"具体怎么解决的

### 3.1 显示 → 自写 ST7735S 驱动 ⭐

设备树里的节点（`dts/ubuntu.dts` 第 824 行）：

```dts
st7735sfb@0x01c0c000 {
    compatible = "allwinner,sun5i-r8,st7735s";     // ← 自定义 compatible
    pinctrl-names = "default";
    pinctrl-0 = <0x20>;
    reg = <0x1c0c000 0x1000>;                       // 显示后端 TCON 基址
    interrupts = <0x2c>;
    dmas = <0x3 0x1 0xe>;
    resets = <0x2 0x6 0x2 0x3 0x2 0x4>;
    reset-names = "lcd", "debe", "defe";
    clocks = <... 8 个时钟 ...>;
    clock-output-names = "tcon-pixel-clock";
};
```

**结论**：面板是 **ST7735S**（128×160 TFT，正好对上原厂 18 张 128×160 的 BMP 开机图），
大佬写了一个 **`st7735sfb` framebuffer 驱动**并编进内核（`cp/modules` 里只有 brcmfmac，说明显示驱动是 built-in）。

> 这也解释了我那份《Alpine 移植指南》里对显示的评估过于悲观 —— 面板型号其实是 ST7735S，不是"未知型号"。

### 3.2 音频 → 绕过 FPGA，用主线 codec

```dts
codec@1c22c00 {
    compatible = "allwinner,sun4i-a10-codec";      // ← 主线 SoC 内置 codec
    reg = <0x1c22c00 0x40>;
    status = "okay";
    allwinner,pa-gpios = <0x15 0x3 0x14 0x0>;      // ← &pio 3 20 0 = PD20，功放使能
};
```

配合 `cp/asound.state`（ALSA mixer 状态，开机由 `alsa-restore` 恢复）：

```
state.sun4icodec {
    control.1 { name 'Power Amplifier Volume'  value 35   /* 0-63 */ }
    control.2 { name 'Line Playback Volume'    value 1 }
    ...
}
```

**结论**：音频链路 = **sun4i-codec → PD20 功放使能 → 喇叭**。
原厂那个"ASoC FPGA"驱动被彻底绕过了 —— 说明 FPGA 在音频上并非必需。

### 3.3 WiFi / 蓝牙

**固件**（`cp/firmware/brcm/`）：
- `brcmfmac43430a0-sdio.bin` —— 主线驱动固件
- `brcmfmac43430a0-sdio.txt` —— **与原厂 `nvram_ap6212.txt` 逐字节完全相同**（我 diff 过）
- `bcm43438a0.hcd` —— 蓝牙 RAM patch

**内核模块**（`cp/modules/6.1.9/`）只有 2 个：
```
kernel/drivers/net/wireless/broadcom/brcm80211/brcmfmac/brcmfmac.ko
kernel/drivers/net/wireless/broadcom/brcm80211/brcmutil/brcmutil.ko
```

**蓝牙启动**（`cp/btstart.service`）：
```
ExecStart=/usr/bin/brcm_patchram_plus -d --patchram /lib/firmware/brcm/bcm43438a0.hcd \\
          --enable_hci --no2bytes --tosleep 1000 --baudrate 1500000 /dev/ttyS3
```

### 3.4 蓝牙其实是一整套方案（后续追加，设备上现编）⭐

蓝牙**不是**镜像里自带的，而是后来单独刷的安装包 `bluetooth-2204-images10-260118.tar.gz`：

> 版本串：**`AKU-BLUETOOTH-260118版固件-蓝牙单独安装包最终版本`**
> 作者：zheng1 (juping_zheng1@163.com)、Ice_BingQi、trz0332、HM

它里面装的是 **BlueZ 5.85 + bluez-alsa 的完整源码树**，由设备联网后现场 `./configure && make && make install`。

```
BCM43438 ──UART3 /dev/ttyS3 @1.5Mbps──▶ btstart.service
                                        brcm_patchram_plus --patchram bcm43438a0.hcd
                                            │
                                            ▼ hci0
                                     bluetooth.service  (BlueZ 5.85, --enable-experimental)
                                        ├─ aku-bluetooth-agent.service → aku_auto_pair（自动配对）
                                        ├─ aku-volume.service         → aku_volum（按键调音量）
                                        └─ bluealsad.service          → bluealsad -p a2dp-sink -c AAC -c SBC
                                              │
                                              ▼
                                        bluealsad-aplay.service → bluealsa-aplay -S
                                              │
                                              ▼
                                        ALSA(sun4i-codec) → PD20 功放 → 喇叭
```

**一句话：这套东西把 AKU 做成了一个支持 AAC 的蓝牙音箱（A2DP sink）。**

> 详细拆解（install.sh 逐段、组件清单、编解码器支持、Alpine 移植步骤）见

| 文件 | Ubuntu (images10) | Alpine (aimages) | 是否相同 |
|---|---|---|---|
| `uImage` | 5,947,120 B | 5,947,120 B | ✅ **MD5 完全相同** |
| `sunxi-spl-with-ecc.bin` | 214,464 B | 214,464 B | ✅ **MD5 完全相同** |
| `u-boot-sunxi-with-spl.bin` | 781,352 B | 781,352 B | ✅ **MD5 完全相同** |

### 4.1 DTB 的 5 处差异（全部在 WiFi 上）⭐

`diff dts/ubuntu.dts dts/alpine.dts`：

```diff
--- UBUNTU
+++ ALPINE
@@ WiFi SDIO 节点 (mmc@1c11000) @@
 			bus-width = <0x4>;
+			max-frequency = <0x989680>;        // 10 MHz
 			non-removable;

@@ PD18 引脚 pinctrl @@
 				function = "gpio_out";
+				output-high;                        // WL_REG_ON 上电默认拉高

@@ wifi_reg_en (mmc-pwrseq-simple) @@
 		reset-gpios = <0x15 0x3 0x12 0x1>;      // &pio 3 18 1 = PD18，低有效
+		post-power-on-delay-ms = <0x1f4>;       // 500 ms
+		power-off-delay-us = <0x2710>;          // 10 ms
+		clocks = <0x13>;                        // &clk_32k (osc32k, 32768 Hz)
+		clock-names = "ext_clock";
 		phandle = <0xf>;
```

**这 5 个属性全是在补 WiFi 模组的电源时序和 SDIO 时钟。**
**好消息：Alpine DTB 是 Ubuntu DTB 的严格超集**（diff 里只有 `+` 没有 `-`）。
**所以把 Alpine 的 DTB 刷到 Ubuntu 系统上，就能白拿这些修复。**

> 可直接照做的修复步骤见 `WiFi蓝牙问题诊断与修复.md`

### 两套系统逐项对照

| 项目 | 原厂 | Ubuntu | Alpine |
|---|---|---|---|
| 管制域库 `regulatory.db` | 不适用 | ❌ **没有** | ✅ **有**（装了 `wireless-regdb`） |
| WiFi 省电 | 无强制 | ❌ NM 强制开 | ✅ 无 NetworkManager |
| DTB WiFi 修复（5 项） | fex 里 | ❌ 缺 | ✅ 有 |

### 四句话总结

1. **两边各对一半**：Ubuntu 的 **WiFi 配置**有问题，Alpine 的**蓝牙配置**有问题。
2. **WiFi 变差是纯配置问题**（省电 + 管制域 + DTB），不是驱动能力不足 —— **可以修**，而且你的 Alpine 已经修好了两项。
3. **Alpine 的蓝牙可能比 Ubuntu 更糟**：HCD 补丁文件放进去了，却没有任何程序加载它，芯片跑在出厂 ROM 固件上。
4. **蓝牙还要先核实串口**：原厂用 `ttyS1`（硬件 UART1），新系统用 `ttyS3`（硬件 UART3），先量清楚再动手。

## 7. 刷机流程（从脚本还原）

```bash
# 在 PC 上跑，需要设备进 FEL 模式
cd images10
# 全量刷（会 nand erase.chip！）
sunxi-fel -p uboot u-boot-sunxi-with-spl.bin \\
    write 0x8a000000 u-boot-dtb.bin \\
    write 0x83000000 sunxi-spl-with-ecc.bin \\
    write 0x41000000 sun5i_r8_akubox_linux.dtb \\
    write 0x40008000 uImage \\
    write 0x50000000 rootfs.ubi \\
    write 0x60000000 u-boot-flash-all.env
```

三个 `.env` 的区别：

| 文件 | 作用 | 风险 |
|---|---|---|
| `u-boot-flash-all.env` | **全片擦除** `nand scrub.chip` + 写全部 + 重启 | 🔴 最高，会清空一切 |
| `u-boot-flash-kernel.env` | 只擦/写 **DTB + 内核**，保留 rootfs | 🟢 低，改 DTB/内核用这个 |
| `u-boot-debug-kernel.env` | 直接从 RAM 启动，**什么都不写** | 🟢 调试用，零风险 |

> **改 DTB 就用 `debug_kernel.sh` 先验证，再 `flash_kernel.sh` 落盘。** 这是大佬已经铺好的安全路径。

1. **先跑 `debug_kernel.sh`**（零写入）确认系统能起
2. **修 WiFi**：装 `wireless-regdb` + 关省电 + 加 `cfg80211.ieee80211_regdom=CN`
3. **修蓝牙**：先 `dmesg | grep -iE 'btbcm|hci_bcm'` 确认是不是补丁没加载
4. **把 Alpine 的 DTB 用到 Ubuntu 上**，白拿那 5 个 WiFi 修复
5. 确认 **FPGA 和电量计** 是否真的丢了功能
